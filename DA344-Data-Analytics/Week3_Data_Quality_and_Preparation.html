DATA ANALYTICS 344 · WEEK 3

Data Quality and Data Preparation

Data Exploration Part 2: deciding how to correct quality issues, encoding categorical features, transforming continuous features, and preventing data leakage — all documented in a data quality plan.

Week 3 at a glance

Core ideas

  • Week 2 identified issues with the data quality report; Week 3 responds: diagnose → classify → plan → correct → prepare (encode/transform) → validate → update the plan.
  • Every corrective action has a benefit and possible unintended consequences (bias, information loss, distorted distributions, over/underfitting). Always justify and validate.
  • Unusual ≠ invalid. Never remove a value solely because it is numerically distant; valid extremes carry information.
  • Missingness itself can be informative — investigate amount, location and pattern before choosing a response; % missing alone must not decide.
  • All preparation parameters (imputation values, min/max, mean/sd, category levels, resampling) are fitted on the training data only and applied unchanged to validation, test and future data.
  • Resampling for class imbalance is applied to the training data only; validation/test sets are never artificially balanced.

Key definitions

  • Data quality issue — loosely, anything unusual about the data in an analytical base table (ABT).
  • Disguised missing value — a placeholder (e.g. 999, −99 999, 0) standing in for a value that is actually missing.
  • Irregular cardinality — a feature whose number of distinct values does not match expectation (e.g. 1, or N = one per instance).
  • Complete-case analysis — removing every instance that has one or more missing values.
  • Imputation — estimating missing values from observed data (constant, mean/median/mode, KNN, model-based).
  • Missing-value indicator — extra binary feature recording whether a value was originally missing.
  • Outlier — an instance numerically distant from the rest; a suspect, not a confirmed error.
  • Noise — stochastic (random zero-mean fluctuations) or systematic (values dragged one direction, e.g. bad calibration); may affect descriptive or target features.
  • Imbalanced target — skewed class proportions; majority vs minority classes (mild 20–40%, moderate 1–20%, extreme <1% minority).
  • One-hot (dummy) encoding — one binary column per nominal level; ordinal encoding — ordered integers for ordered levels.
  • Data leakage — information from held-out data influencing preparation or training, inflating performance estimates.

Formulas

  • Min–max normalisation to [0,1]: a′i = (ai − min(a)) / (max(a) − min(a)).
  • Standardisation (z-score): a′i = (ai − ā) / sd(a); result has mean 0, sd 1.
  • Log transform: a′i = log(ai) — compresses large values, reduces right skew.
  • Outlier fences (rule of thumb): suspect values below Q1 − 1.5×IQR or above Q3 + 1.5×IQR; clamp thresholds often set to these fences.

Exam traps

  • Choosing a missing-value response from the % missing alone.
  • Treating disguised missing values (999) as real numbers — they distort means, sds and models.
  • Deleting valid extreme observations just because they look unusual.
  • Recomputing min/max or mean/sd with validation/test/new data included — that is leakage.
  • Balancing the validation or test set, or judging an imbalance model by accuracy (always-predict-majority scores 96% on a 96/4 target).
  • One-hot encoding an ordinal feature, or integer-encoding a nominal one (e.g. zip codes as numbers).
  • Imputing an informative-missingness feature without adding an indicator.

01From diagnosis to action: where Week 3 fits

Week 2 built the data quality report to understand an analytical base table (ABT) and flag potential problems. Week 3 keeps that report as the starting point, but the question changes from “what looks unusual?” to “what do we do about it, why, and how do we check the result?” The week ends with a prepared ABT that is encoded, transformed and documented — ready for modelling. (The practical component of this week is implemented in R; the notes below focus on the theory, which is tool-agnostic.)

1.1 The data quality report, recap

The report has tabular summaries plus a visualisation per feature, split by feature type:

1.2 What the report flagged in the motor-insurance example

  • Income: many zeros — possibly disguised missing values.
  • Claim amount: minimum of −99 999 — likely a data-entry mistake or system default (invalid value / disguised missing).
  • Num. claims, Amount received: irregular maximum values — possibly a company policy limit (needs domain investigation).
  • Num. soft tissue: 2% missing values.
  • Fraud flag: categorical target stored as continuous; target unbalanced.
  • Insurance type: cardinality 1 — constant feature, removable.
  • Marital status: 61.2% missing — many models cannot handle this.

Each flagged issue now needs a decision, a justification, and a validation step — the machinery of the rest of these notes.

02Classifying issues and understanding their impact

Definition

A data quality issue is loosely defined as anything unusual about the data in an ABT. Common families: missing values, disguised missing values, irregular cardinality, skew/imbalanced target, outliers and noise. Issues arise either from invalid data (errors in the process that generated the ABT, often in derived-feature calculations) or from valid data that is unusual for domain-specific reasons.

2.1 Three-way classification

When the report flags something, classify it before acting:

  1. Confirmed data error — evidence shows the value cannot be correct (e.g. a negative claim amount that is a system default; a sensor code 999°C recorded whenever communication is lost; planned shutdowns recorded as failures). Fix or recode it.
  2. Unusual but valid observation — extreme, yet confirmed plausible by domain knowledge (e.g. 412 days since maintenance, confirmed by the maintenance manager; high vibration on a machine standing next to an industrial press). Keep it, possibly with a robust treatment (Section 7).
  3. Needs domain investigation — evidence is insufficient either way (e.g. irregular maxima that might be a company policy cap). Investigate before changing anything.

2.2 Why quality issues matter

  • Summaries: disguised missing values and outliers distort means, standard deviations and correlations (a single −99 999 pulls the mean and inflates the sd).
  • Training: error-based models cannot be trained on missing values; similarity-based models are strongly distorted by outliers and unscaled features; inconsistent labels create spurious categories.
  • Performance: noisy target labels make the true relationship unlearnable and make performance estimates unreliable.
  • Conclusions: biased handling of missing data (e.g. dropping patients who left a trial due to adverse effects) can make a treatment look better than it is.
Common mistake

Acting before classifying. Removing, imputing or capping a value that is actually valid and informative destroys signal; conversely, keeping a confirmed error contaminates everything downstream. Classify first, then choose a response, then validate.

03Missing values: amount, location and pattern

Definition

Disguised missing values are placeholders submitted or recorded in place of an unknown value — e.g. users entering incorrect values for mandatory fields they do not want to disclose, or systems writing codes like 999 or −99 999. They must be recoded to genuine missing values before any analysis.

Missing values are a normal occurrence in real data sets. Common causes:

  • Data integration errors — two data sets merged on a key where one side lacks that key value.
  • Random events — any measurement process is vulnerable: dead device batteries, misplaced samples, sensor dropouts.
  • Specific causes — systematic reasons, e.g. patients dropping out of a clinical trial, or a test performed only under certain conditions.
Intuition

A missing value is not necessarily an error — and it can be informative. In the lecture example, the feature pregnant is missing whenever gender is male: the missingness itself tells you something. Likewise, an oil-analysis result missing because the test is only ordered when a technician suspects trouble is a strong signal about machine condition. Imputation or deletion that ignores this throws information away.

3.1 Investigating missingness

  • Amount — the % Missing column of the data quality report, per feature.
  • Location — where values are missing. A missingness heatmap (rows = instances, columns = features, colour = missing/complete) shows which instances and features are affected, and clustering the rows reveals groups of instances with similar missingness.
  • Pattern — a co-occurrence plot displays how often feature combinations are missing together (e.g. taper and a laboratory measurement missing together most frequently), and pairwise scatter plots can show missing values as marks on the axis margins, revealing relationships between missingness in one feature and values of another (e.g. diameter unmeasurable exactly when samples are flat).
  • Information content — ask: does the fact that a value is missing help predict the target? If yes, preserve that signal (retain missingness or add an indicator).

04Responding to missing values

Whatever the cause, an explicit decision must be made. The five standard responses, with their trade-offs:

Responses to missing values: when each is appropriate, one benefit and one unintended consequence.
ResponseWhen appropriateBenefitUnintended consequence
Retain (do nothing) The chosen model supports missing values natively (e.g. some tree-based models using surrogate splits). No information destroyed; missingness stays usable as a signal. Most predictive modelling techniques cannot handle missing values at all; model choice becomes constrained.
Remove feature Very high % missing and the feature adds little unique value. Simplest fix; cleans the table quickly. Informative, non-redundant features can be lost — including the information contained in the missingness itself.
Remove instances (complete-case analysis) Few instances affected; data plentiful and missingness plausibly random. Simple; remaining rows are complete. Throws away data; can bias the feature–target relationship if missingness is not random (e.g. dropping trial patients who suffered adverse effects makes the treatment look better).
Impute (numeric or categorical) Moderate missingness; plausible estimates available. Keeps instances and features; most models can then be used. Imputation is an estimate, not truth: it can distort distributions, underestimate variance and erase missingness information.
Missing-value indicator Missingness may be informative; usually combined with imputation. Preserves the missingness signal as an explicit feature. Adds a feature that may be useless (or spurious) if missingness is truly random; sparse indicator can complicate training.
Common mistake

Deciding on the percentage missing alone. A feature with 62% missing can be the most informative feature in the table (oil analysis ordered only when trouble is suspected), while a feature with 1% missing can be useless. Consider: why values are missing, whether missingness is informative, how much data is affected, and what the model requires.

4.1 Imputation methods

  • Constant — replace all missing values with a fixed value (e.g. 0).
  • Central tendency — continuous: mean, or median if outliers are present; categorical: mode (most frequent level). In the lecture example, income missing values were imputed with the observed mean 90 555.
  • K-nearest neighbour — for small/moderate data: find the K most similar complete instances (e.g. by Euclidean distance) and impute the mean of their values. Effective but expensive for large data.
  • Model-based — predict the missing value from the other features.

When selecting an imputation method, consider: tolerance to other missing values (within an instance, other features may also be missing), speed (imputation is a model embedded inside the modelling pipeline), compatibility with both numeric and categorical features, and stability (not overly influenced by outlying points).

Worked example 4. Choosing missing-value responses (study guide Q2 data). An ABT predicts whether an industrial machine fails within the next 7 days; one row = one machine at a weekly assessment date.

1. Average vibration — 8% missing, usually missing while the machine is switched off for maintenance.

  • Informative? Yes — missingness marks maintenance windows, which relate to failure risk.
  • Response: impute (median, robust to outliers) and add a missing-value indicator; alternatively retain if the chosen model handles missing values.
  • Justification: 8% is moderate, the feature is plausibly predictive, and the indicator preserves the maintenance-window signal.
  • Unintended consequence: imputed values blur the true vibration behaviour during maintenance windows; the indicator may dominate if maintenance strongly predicts the target.
  • Validation: re-run the quality report: 0% missing, indicator present, distributions before/after imputation compared.

2. Maximum temperature — 0.5% missing on apparently random dates.

  • Informative? No evidence of it — pattern looks random.
  • Response: remove the affected instances (complete-case) — or impute with the median; both defensible at 0.5%.
  • Justification: negligible data loss; random missingness means little bias risk from removal.
  • Unintended consequence: if the missingness is not truly random, removal subtly biases the sample; imputation would slightly shrink variance.
  • Validation: check row count dropped by ~0.5% and summaries are essentially unchanged.

3. Oil analysis result — 62% missing; the test is performed only when a technician suspects a serious problem.

  • Informative? Strongly — “no test” means “no suspected problem”, and “test done” is itself a warning signal.
  • Response: do not remove the feature. Impute the missing results and add an indicator recording that no test was done (or retain missingness if the model supports it).
  • Justification: despite 62% missing, the missingness mechanism is directly related to machine condition and hence to the target.
  • Unintended consequence: imputing without an indicator would fabricate “normal” results for healthy machines and destroy exactly the signal that matters.
  • Validation: confirm the indicator splits instances into tested/untested groups with different failure rates.

4. Machine type — 0.2% missing; recoverable from the asset register.

  • Informative? No — a clerical gap, not a signal.
  • Response: recover the true values from the organisation’s asset register (recovery beats estimation whenever possible).
  • Justification: recovered values are ground truth — no estimation error, no distribution distortion.
  • Unintended consequence: effort/cost of joining; the register itself could be outdated, introducing wrong labels.
  • Validation: spot-check recovered values against physical assets; confirm 0% missing and unchanged cardinality.

05The data quality plan

Definition

The data quality plan records every identified data quality issue together with its handling strategy — one row per issue, with the affected feature, the issue observed, and the action to implement. It is the audit trail that connects evidence to decisions.

For each issue the plan records six things:

  1. Affected feature — which column(s) are involved.
  2. Issue and evidence — what is wrong and how the report/investigation shows it (e.g. “minimum = −99 999, single spike in histogram”).
  3. Corrective action — the specific change to implement (e.g. “recode −99 999 to missing; impute median”).
  4. Rationale — why this action, given the classification (error / valid / investigate) and the trade-offs.
  5. Possible unintended consequences — bias, information loss, distorted distributions, over/underfitting risks.
  6. Validation — the checks that will confirm the result (see Section 13).

06Invalid values, inconsistent labels, duplicates and irregular cardinality

  • Invalid values (confirmed errors, e.g. placeholder codes, impossible readings): recode — to missing, to a corrected value from a trusted source, or to a valid category. Never leave placeholders in as numbers.
  • Inconsistent category labels (Type A / typeA / A / Type-A; male / m / M): standardise to one canonical label per real category, using domain knowledge to decide which spellings are the same category. Irregular cardinalities commonly arise from exactly this kind of inconsistent encoding.
  • Duplicate observations: first investigate (true duplicate extraction vs. two genuinely identical assessments); confirmed duplicates are removed, then row counts and distributions are rechecked.
  • Irregular cardinality — cardinality that does not match expectation:
    • Cardinality 1: the same value for every instance — a constant feature with no predictive power; remove it (e.g. Insurance type = “ci” for all 500 claims).
    • Cardinality N (one unique value per instance): usually a unique identifier — remove it from the descriptive features (Section 9); occasionally it is really a continuous feature in disguise.
    • Cardinality between 1 and N: inspect levels manually and use domain knowledge (e.g. encodings male vs m vs M).
Common mistake

Keeping an identifier (e.g. Machine ID) as an ordinary descriptive feature: with one unique value per instance it cannot generalise to new machines, and similarity- or rule-based models can memorise training rows instead of learning patterns.

07Outliers and noise

Definitions

An outlier is an instance that is numerically different from the rest of the instances. Noise is unwanted disturbance in feature or target values: stochastic noise — random fluctuations with zero mean and small deviation; systematic noise — all values dragged in one direction, e.g. by a badly calibrated instrument.

7.1 Identifying outliers

  • Start with the min/max of each continuous feature and apply domain knowledge (e.g. age cannot be negative).
  • Examine distributions: the textbook’s rule of thumb flags suspected outliers when Q1 − min >> median − Q1, or max − Q3 >> Q3 − median; a common formal rule flags values beyond 1.5 × IQR from the quartiles.
  • Clustering: values that fall outside all clusters are candidate outliers.
\[ \begin{gathered} x \lt \text{Q1} - 1.5 \times \text{IQR} \quad\text{or}\quad x \gt \text{Q3} + 1.5 \times \text{IQR} \\ \text{(suspected outlier fences, where } \text{IQR} = \text{Q3} - \text{Q1}\text{)} \end{gathered} \]
x
A value of the feature.
Q1
First quartile (25th percentile).
Q3
Third quartile (75th percentile).
IQR
Interquartile range, Q3 − Q1: the spread of the middle 50%.
1.5
Conventional multiplier that sets how far beyond the quartiles a value must lie.
Common mistake

The maximum value is not necessarily an outlier, and an observation must never be removed solely because it is far from the mean or median. Statistical distance only raises suspicion; domain knowledge decides. Valid extremes are often the most valuable observations: a machine that ran 412 days without maintenance, or a rare fraud case, teaches the model about the regions it most needs to understand.

7.2 Handling outliers — and comparing consequences

Standard options: (1) do nothing; (2) remove/neutralise outliers statistically, e.g. a clamp transformation; (3) remove outliers during training (e.g. by monitoring training errors — instances that persistently produce large errors while the rest of the training error shrinks form a second mode in the error distribution and can be removed); (4) keep outliers but use models/loss functions less sensitive to them (e.g. replacing squared-error loss with a loss that grows linearly for large errors).

\[ a'_i = \begin{cases} \text{lower} & \text{if } a_i \lt \text{lower} \\ \text{upper} & \text{if } a_i \gt \text{upper} \\ a_i & \text{otherwise} \end{cases} \qquad \text{(clamp transformation)} \]
ai
Original value of feature a for instance i.
a′i
The value after clamping.
lower, upper
The chosen thresholds; values beyond them are pulled back to the threshold.

A common choice sets lower = Q1 − 1.5×IQR and upper = Q3 + 1.5×IQR. Note the clamp thresholds, like all preparation parameters, must be computed from the training data only.

7.3 Noise

  • Noise occurs in descriptive features (erroneous or missing readings) and in the target feature (mislabelled or contradictory examples). Noisy targets are worse: the model cannot learn a relationship that contradicts its own training labels, performance estimates become pessimistic or unstable, and the model may latch onto spurious features to explain the noise.
  • Stochastic noise is largely handled by the learning process itself; systematic noise can often be corrected or removed, commonly with a nearest-neighbour approach (an instance surrounded by neighbours of a different value/label is suspect).
  • For noisy target labels, a graph-based view is useful: connect each instance to its nearest neighbours; edges joining different classes are cut edges. An instance with one cut edge sits on a genuine decision boundary (keep); an instance with many cut edges indicates a noisy pattern (correct or remove).
  • If noise is present and the model is too complex, overfitting results — the model memorises the noise.

Reading  Kelleher et al. (2e), Ch 3 §3.4–3.7 — treating missing, noisy and duplicate data, including clamping and related transformations.

08Class imbalance in the target

Definition

An imbalanced data set has skewed class proportions: the vast majority of instances belong to one class (the majority class) and few to the other (the minority class). Imbalance is common in medical classification and predictive maintenance. Degree of imbalance by minority-class proportion: mild 20–40%, moderate 1–20%, extreme <1%. Class imbalance is considered for the target feature, because it is the classes the model must predict; imbalance in a descriptive feature is just a distribution fact.

Intuition — the accuracy paradox

With 4 992 non-failures and 208 failures (96%/4%), a model that always predicts “No failure” scores 96% accuracy while detecting zero failures. Most predictive models, by default, give every instance equal importance and will happily exploit this: they learn to predict the majority class because misclassifying the minority barely costs them anything, even though the cost of a missed failure may be enormous. Accuracy alone is therefore a misleading metric under imbalance.

8.1 Responses to imbalance

  • Oversampling — sample the minority class with replacement until it matches the majority class size. Benefit: no data discarded. Risk: duplicated instances can lead to overfitting.
  • Undersampling — sample the majority class without replacement down to the minority size. Benefit: smaller, faster training set. Risk: discards data, which can cause underfitting.
  • Synthetic sampling (SMOTE-style) — create new minority instances by interpolating between a minority instance and one of its k nearest minority neighbours: take the difference vector to the neighbour, multiply it by a random number in [0,1], and add it to the original instance. Benefit: more realistic variety than simple duplication. Risk: synthetic points may drift into the majority region and blur the true boundary.
  • Algorithm-level weighting — keep the data as-is but assign higher weight to minority instances (or penalise minority-class errors more heavily) during training.
  • Other routes mentioned in the lectures: targeted undersampling that removes majority instances likely to be noise or boundary cases (Tomek-link pairs — two mutually nearest neighbours of different classes), and reframing the task as abnormality detection.
Common mistake

Resampling must be applied to the training data only. The validation and test sets must keep the real-world class proportions, otherwise performance estimates are computed on a distribution the deployed model will never see and become optimistically biased. Likewise, any synthetic instances must be generated from training neighbours only — building them from points that include validation/test data is leakage.

Worked example (imbalance arithmetic). The ABT has 5 200 instances: 4 992 “No failure” (96%) and 208 “Failure” (4%).

(a) Yes, the target is imbalanced: the minority class is only 4% of the data (moderate imbalance on the 1–20% scale). (b) A model that always predicts “No failure” is correct on 4 992 of 5 200 instances: accuracy = 4992/5200 = 0.96 = 96%. (c) This is misleading because the model detects no failures at all — the class that matters most is never predicted; accuracy rewards predicting the majority class. (d) Responses such as oversampling the minority, undersampling the majority, synthetic sampling, or class weighting should be considered, applied to the training data only (Figure 3.2).

09Feature removal and recoding before modelling

Not every column of the ABT should enter the model as a descriptive feature. Decide for each feature whether to remove, retain or recode it:

  • Constant features (cardinality 1): no variation, no predictive power — remove.
  • Identifiers (cardinality N, e.g. Machine ID): needed to track rows but useless and dangerous as features — remove from the descriptive features.
  • Redundant features: measure almost the same thing as another feature (e.g. AverageVibration and VibrationRMS with correlation 0.98) — keep one, remove the other.
  • Invalid features: built from erroneous or placeholder data with no trustworthy fix — remove or rebuild.
  • Features unavailable at prediction time: e.g. a maintenance-work-order feature that only exists after a failure has occurred. Such a feature cannot be known when a prediction is required; keeping it also leaks the target. Remove.
Intuition

Ask of every feature: “when I must predict for a new machine next week, will this value actually be available, and will it mean the same thing?” If not, the feature cannot be used, however predictive it looks historically.

10Encoding categorical features

Most machine-learning algorithms require numerical input, so categorical features must be encoded — and the encoding must respect the feature’s type:

  • Nominal features (no natural order): use one-hot / dummy encoding — one binary column per level. A linear model can then learn a separate parameter per level.
  • Ordinal features (natural order): use ordered integers (e.g. Low = 1, Medium = 2, High = 3), preserving the order in a single column.
Common mistake

Encoding a nominal feature as a single integer fabricates order and distances that do not exist: representing zip codes as numbers asks the model to treat 20004 as “twice” 10002, instead of learning a separate signal per zip code. Conversely, one-hot encoding an ordinal feature discards its ordering (and spreads one concept over several columns). Match the encoding to the feature type and check compatibility with the chosen algorithm.

Justification of the pairing: one-hot suits nominal features because it represents each level independently with no implied order or distance; ordered integers suit ordinal features because they preserve the rank order in one dimension. The encoding must also be compatible with the selected algorithm (e.g. similarity-based learners need encodings under which distances make sense).

11Transforming continuous features

Transformations change the representation of a feature — its scale or shape — so that algorithms whose mathematics assumes comparable scales or well-behaved distributions work properly. Every transformation changes what the numbers mean, and some information may be lost or distorted.

11.1 Logarithmic transformation

\[ a'_i = \log(a_i) \]
a′i
Transformed value.
ai
Original value; must be positive.
log
Logarithm.

Applied to each (positive) value of a feature. The log compresses large values much more than small ones, so a long right tail is pulled in and a right-skewed distribution becomes more symmetric. Interpretation shifts from additive to multiplicative differences. Information distorted: original magnitudes are no longer directly comparable, and zero or negative values cannot be logged without adjustment.

11.2 Min–max (range) normalisation

Linear scaling of the original values into a chosen range, typically [0,1] (or [−1,1]). The general form scales into [old, new]:

\[ a'_i = \frac{a_i - \min(a)}{\max(a) - \min(a)} \times (\text{new} - \text{old}) + \text{old} \]
a′i
Normalised value.
ai
Original value.
min(a), max(a)
Smallest and largest value of the feature in the training data.
old, new
Lower and upper bound of the target range, written [old, new] in these notes; 0 and 1 for the usual case.

For the usual [0,1] range the multiplication and addition disappear and only the fraction remains. Works well when good bounds on the data are known and outliers are few (e.g. age); works poorly when one extreme value squeezes everyone else into a tiny part of the scale (e.g. income). New observations beyond the training range fall outside [0,1] — which is correct behaviour when training parameters are applied.

11.3 Standardisation (z-score)

Expresses how many standard deviations a value lies from the mean:

\[ \begin{gathered} a'_i = \frac{a_i - \bar{a}}{\operatorname{sd}(a)} \\ \text{where } \bar{a} \text{ is the mean and } \operatorname{sd}(a) \text{ the standard deviation of the feature} \end{gathered} \]
a′i
Standard score: how many standard deviations the value lies from the mean.
ai
Original value.
ā
Mean of the feature in the training data.
sd(a)
Standard deviation of the feature in the training data.

The transformed feature has mean 0 and standard deviation 1, but no fixed bounds — values can exceed ±1, which is fine. Standardisation is less distorted by extremes than min–max, but the results are less intuitively bounded.

11.4 Discretisation (binning)

Converts a continuous feature into a categorical one by assigning values to bins. Equal-width binning splits the value range into b bins each of width range/b; equal-frequency binning sorts values and places an equal number of instances in each bin (useful for probability-based learners). Choosing b is a trade-off: too few bins lose distributional information (a bi-modal shape can vanish into 3 bins); too many bins give an accurate picture but leave bins with no instances.

Common mistake

Information lost or distorted by transformations: discretisation throws away within-bin differences entirely; min–max makes every scaled value depend on the two most extreme observations; standardisation changes the meaning of values to “distance from the mean in sds”; log changes additive differences into multiplicative ones. Be able to state, for any transformation, what changed and what was lost.

Worked example 1. Min–max normalisation with a new observation (study guide Q6 data). Training values: Vibration = 2.0, 4.0, 6.0, 8.0 and Days since maintenance = 10, 30, 50, 70.

Step 1 — training parameters. Vibration: min = 2.0, max = 8.0, range = 6.0. Days: min = 10, max = 70, range = 60.

Step 2 — normalise the training values using a′ = (a − min)/(max − min):

InstanceVibrationNormalised vibrationDaysNormalised days
M012.0(2−2)/6 = 0.00010(10−10)/60 = 0.000
M024.0(4−2)/6 = 0.33330(30−10)/60 = 0.333
M036.0(6−2)/6 = 0.66750(50−10)/60 = 0.667
M048.0(8−2)/6 = 1.00070(70−10)/60 = 1.000

Step 3 — transform the new observation (vibration 5.0, 90 days) with the training parameters only:

  • Vibration: (5.0 − 2.0)/6.0 = 3.0/6.0 = 0.500.
  • Days: (90 − 10)/60 = 80/60 = 1.333 — outside [0,1], because 90 exceeds the training maximum. That is expected and correct.

Why the parameters must not be recomputed with the new value: if 90 were included, the new maximum would become 90 and every training value would be rescaled differently ((70−10)/80 = 0.75 instead of 1.0), so training and new data would live on different scales. More fundamentally, letting held-out or future observations influence the scaling parameters lets information about them leak into preparation, giving optimistically biased results; in production, future values are unknown at training time anyway, so the only consistent rule is: fit once on training data, apply forever.

Worked example 2. Standardisation of a test observation (study guide Q8 data). A numeric feature has training-set mean 50 and training-set standard deviation 10. A test observation has value 80.

Standardised value using the training parameters: z = (80 − 50)/10 = 30/10 = 3.0. The test observation lies 3 standard deviations above the training mean — a genuinely extreme value, correctly signalled.

Why the test-set statistics must not be used: the test set reported mean 60 and sd 8, which would give (80 − 60)/8 = 2.5. Using those numbers is leakage: the standardised value would then depend on the distribution of the very data used to evaluate the model, so preparation and evaluation are no longer independent, performance estimates become optimistically biased, and scores are no longer comparable with the training data (which was standardised differently). The same reasoning applies to validation data and to future observations: always apply the training mean and sd.

Reading  Kelleher et al. (2e), Ch 3 §3.4–3.7 — normalisation (range normalisation, standardisation), binning/discretisation and related feature transformations.

12Preventing data leakage during preparation

Definition

Data leakage in preparation occurs when information from the validation set, test set or future observations is used to shape how the model is built — directly or through preparation parameters — producing performance estimates that are too optimistic and behaviour that will not reproduce in deployment.

The following must all be determined from the training data only:

  • numerical imputation values (means, medians, modes, KNN neighbours);
  • data-derived category levels and encoding rules (which levels exist, one-hot columns, ordinal mappings);
  • normalisation parameters (min and max);
  • standardisation parameters (mean and standard deviation);
  • outlier thresholds (e.g. clamp fences from quartiles/IQR);
  • resampling procedures (over/under/synthetic sampling of the training classes).

The resulting rules are then applied unchanged to the validation data, the test data, and every future observation. A level never seen in training has no encoding column; a value beyond the training range simply falls outside [0,1].

Common mistake

Running imputation, scaling or resampling on the whole table before splitting into training/validation/test. Even though no labels are used, the distributions of the held-out rows have then shaped the preparation — a subtle but real leak. Split first; fit preparation on the training part only.

13Validating the prepared table and closing the loop

After all corrections, encodings and transformations, the prepared ABT must be checked before modelling — essentially a fresh, focused data quality report:

  • Dimensions — row count matches expectations after instance removals/deduplication; column count reflects removed, added (indicators, one-hot columns) and recoded features.
  • Missingness — remaining missing values are as planned (often 0%, or retained deliberately); indicators exist where promised.
  • Data types — continuous features numeric, categorical features categorical (no categorical target stored as a number).
  • Category levels — canonical labels only; no inconsistent spellings; levels match those derived from the training data.
  • Value ranges — normalised features in [0,1] for training rows; standardised features with training mean 0 and sd 1; no placeholder codes (999, −99 999) anywhere.
  • Distributions — histograms compared before/after each transformation to confirm the intended effect (e.g. skew reduced) and to catch distortions.
  • Target balance — training set rebalanced as planned; validation/test sets left at natural proportions.

Finally, update the data quality plan: record the actions actually implemented and the validation evidence that the prepared data are suitable for modelling. The plan then documents the complete chain from raw ABT to modelling-ready table — which is exactly what an examiner (or an auditor) can question you on.
