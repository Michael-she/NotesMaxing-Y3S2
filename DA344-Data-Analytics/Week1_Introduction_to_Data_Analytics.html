DATA ANALYTICS 344 · WEEK 1

Introduction to Data Analytics

Topics 1 & 2: what data analytics is, how machine-learning problems are recognised and formulated, how data is structured for prediction (analytics base table), and how models are developed and evaluated within CRISP-DM.

Week 1 at a glance

Core ideas

  • Data analytics transforms raw data into insights and knowledge that support engineering and business decisions.
  • Machine learning learns the rules/logic from historical data instead of having them hand-coded; it is the engine of predictive analytics.
  • Three learning paradigms: supervised (target known), unsupervised (no target), reinforcement (learn by rewards). Supervised tasks split into classification (discrete target) and regression (continuous target).
  • A real-world problem becomes an analytics problem by fixing: the decision/process supported, the objective, the prediction subject, the required model output, and how the output is used — then checking feasibility (data available, available at prediction time, organisation can act).
  • Domain concept diagrams turn an analytics solution into candidate descriptive and target features; features are screened for availability, timing, longevity.
  • The analytics base table (ABT): one row = one prediction subject; descriptive feature columns + one target feature column.
  • CRISP-DM has six phases (business understanding, data understanding, data preparation, modelling, evaluation, deployment) and is iterative.
  • A model must generalise: training data develops it, validation data selects it, test data gives the final unbiased estimate of deployment performance. Training performance alone proves nothing.

Key definitions

  • Data — raw, unprocessed facts and measurements. Information — data processed into a meaningful form. Knowledge — information understood well enough to guide decisions and action.
  • Data analytics — extracting useful insights from raw data using an explorative/data-driven approach; related to data mining (discovering valuable information in small and very large databases).
  • Machine learning — a subfield of AI that gives computers the ability to learn without being explicitly programmed (Samuel, 1959).
  • Generalisation — performing well on both seen (training) and unseen instances.
  • Underfitting — model too simple to capture the true relationship (high bias). Overfitting — model fits training data too closely, becomes sensitive to noise (high variance).
  • Feature — a measurable property of the prediction subject (also: attribute, field, variable). Instance — one row/subject (also: example, record, observation).

Formulas

  • Accuracy = (TP + TN) / (TP + FP + FN + TN);  Precision = TP / (TP + FP);  Recall = TP / (TP + FN)
  • F1 = 2 × (Precision × Recall) / (Precision + Recall) — harmonic mean, 0 to 1.
  • SSE = Σ(ti − M(di))²;  MSE = SSE / n;  RMSE = √MSE (same units as target).
  • R² = 1 − SSE/SST, where SST = Σ(ti − t̄)² (total sum of squares about the mean). R² = 0: explains no variance; R² = 1: explains all.

Exam traps

  • High accuracy on imbalanced data is misleading — compare against the “predict the majority class” baseline; check precision/recall.
  • Positive class = the business-important outcome (e.g. defective, fraud). FP/FN labels depend on it.
  • The confusion matrix only reflects one classification threshold (usually 0.5) applied to the model’s prediction score — the ROC curve shows performance across all thresholds.
  • Residual = actual − predicted. Negative residual → model overestimated.
  • Never select models using the test set — that makes the test estimate optimistic; selection uses the validation set.
  • 100% training accuracy can mean memorisation (overfitting), not a good model.
  • A feature recorded historically can still be invalid if it is not available at prediction time (timing) or will change/become stale (longevity).
  • One row of the ABT = one prediction subject — not one measurement, day or transaction unless that is the subject.

01Data analytics: from data to decisions

Organisations in almost every industry are now data-capturing: sensors, transactions, images, documents and logs are collected continuously. On its own this data is an untapped asset. Data analytics is what turns it into value — improved revenue, reduced costs, business agility, better customer experience, and new or improved products — by revealing meaningful information that supports better decision-making. The lectures open with examples where tiny data-driven edges decide outcomes (the Olympic crouching start, Moneyball’s Oakland A’s recruitment, Formula 1 cars streaming over a million data points per second from ~300 sensors).

Definition — data analytics

Data analytics refers to (i) the process of extracting useful insights from raw data, (ii) using an explorative or data-driven approach, (iii) that shares similarities with data mining — the process of discovering valuable information from small and very large databases using algorithms that discover hidden patterns in the data.

1.1 Data, information, knowledge

Analytics is often described as a chain that adds meaning at each step:

  • Data — raw, unorganised facts and measurements (numbers, text, signals, images) with no meaning attached, e.g. a stream of sensor readings or a log of order records.
  • Information — data that has been processed, organised or structured so that it becomes meaningful and useful, e.g. completion times summarised per component type.
  • Knowledge — information that has been understood and internalised well enough to guide decisions and action, e.g. knowing which design characteristics drive long completion times, and using that to promise realistic delivery dates.

The lecture’s input–process–output picture is the same idea: inputs (data) go through the analytics process and come out as outputs (insights/knowledge) that improve a decision — in their analogy, turning a high-school student into an engineer by improving the pass rate.

Intuition

Data answers “what was recorded?”, information answers “what does it mean?”, and knowledge answers “what should we do about it?”. Predictive analytics pushes one step further: it uses knowledge learned from the past to predict the future before data about it exists.

1.2 Data modalities and analytics families

Data comes in several common modalities, and each has a corresponding family of analytics. The module framework lists these explicitly for Topic 1:

Data modalityAnalytics familyTypical question
Structured (tabular) dataVisual analytics / exploratory analyticsWhat patterns, trends and outliers do the records show?
TextText analyticsWhat topics or sentiment appear in documents?
ImagesImage analyticsIs this manufactured component defective?
AudioAudio analyticsDoes this machine sound abnormal?
Time seriesTime-series analyticsWhat will demand/energy consumption be next month?
Common data modalities and the analytics families that process them.

Big data refers to data sets whose volume, speed of arrival, and variety exceed what traditional tools can store and process easily; extracting value from them requires scalable, algorithmic approaches (this is why dimensionality reduction, for instance, is used for big-data visualisation and compression).

Predictive analytics is the branch of analytics that builds models of the past in order to predict future or unknown outcomes. Its core tool is machine learning, covered next. Sample business cases from the lectures: predicting when a component will fail (remaining useful life), detecting anomalies in engineering systems, forecasting building energy consumption, and improving autonomous-vehicle navigation.

02Machine learning and the three learning paradigms

Definition — machine learning

“Machine learning is the field of study that gives computers the ability to learn without being explicitly programmed” (Arthur Samuel, 1959). It is a subfield of artificial intelligence in which models learn or self-discover the business logic or rules from historic data, rather than having the rules hand-coded by a domain expert.

Classical vs machine-learning programming. In classical programming, domain knowledge is written as explicit rules (e.g. the ABCD melanoma test becomes a chain of IF–THEN statements). In machine learning, the algorithm is instead shown labelled examples (e.g. images of malignant and benign lesions) and discovers its own decision rules from them. Tom Mitchell’s 1998 formulation makes “learning” precise: a computer program learns from experience E with respect to some task T and performance measure P if its performance on T, as measured by P, improves with experience E — for example, a spam filter (T: classify email; P: fraction correctly classified; E: the labelled training emails) or an energy-output predictor whose parameters are updated to minimise the summed squared error between predicted and actual output.

2.1 The three paradigms

Supervised learningUnsupervised learningReinforcement learning
What is it? An algorithm uses training data (with human-assigned labels) to learn the relationship between a set of descriptive features and a target feature. An algorithm explores data described by descriptive features without an explicit target, inferring structure (e.g. clusters of similar customers). An algorithm learns to perform a task by taking actions in an environment and maximising the rewards it receives.
When to use? You know how the inputs should be labelled and what behaviour to predict, but need the algorithm to compute it for new data. You do not know how to classify the data and want the algorithm to find underlying patterns. Little labelled training data; no clearly defined ideal end state, but an environment to learn from.
How it works 1. Collect and label sample data. 2. Train a model on the descriptive–target relationship. 3. Apply the model to new data once accurate enough. 1. Receive unlabelled data. 2. Infer structure. 3. Identify groups with similar behaviour (e.g. buying behaviour). 1. Take an action. 2. Receive a reward if it moves toward maximising total reward. 3. Correct itself over time to optimise the sequence of actions.
Examples Defect detection, spam filtering, medical diagnosis, price/stock forecasting. Market segmentation, recommendation systems, big-data visualisation, data compression (clustering; dimensionality reduction). Robot navigation, autonomous vehicles, automated stock trading.
The three machine-learning paradigms as presented in the Week 1 lectures.
Common mistake

Reinforcement learning is not supervised learning with delayed labels: there is no target feature, only a reward signal that evaluates actions. If a question describes an agent making sequential decisions in an environment (e.g. routing parts between machines to minimise waiting times, where each decision affects later parts), the answer is reinforcement learning.

2.2 Classification vs regression (supervised sub-tasks)

  • Classification: the target feature is discrete (a category or class). The model learns a function that separates the classes. Examples: spam or not spam; account hacked or not; component defective or non-defective.
  • Regression: the target feature is continuous (a quantity). The model learns a function mapping inputs to a number. Examples: predicting a house’s selling price from its size; the number of shares traded tomorrow; completion time of an order in working days.
Intuition — deciding the task type

Ask one question: what exactly must the model output? A label/category → classification. A number you can meaningfully add, average or be “off by 2.3” on → regression. The input modality (image, text, table) does not decide this — an image-based defect check is still classification.

2.3 How supervised learning is framed formally

Given training examples consisting of descriptive-feature vectors d[i] with target values t[i], produced by some unknown function M : d → t, the goal is to find a good approximation to M. Machine learning does this by searching a space of candidate models (equations, rule sets, lookup tables, or combinations) for the one that best captures the descriptive–target relationship. Later topics in DA344 are different ways of running that search: rule-based learning (if-else trees), similarity-based learning (predict the target of the most similar known instance), error-based learning (adjust parameters to minimise error), and ensemble learning (combine models).

Two important consequences of this framing:

  • Consistency is not unique. A model is consistent with a data set if it predicts every training instance correctly. With 4 binary features there are 24 = 16 possible instances and a binary target, so 216 = 65 536 different prediction functions exist; the 7 training rows reduce these to 512 consistent models. The training data alone cannot pick one — machine learning is an ill-defined problem.
  • Consistency is not learning. A consistent model can simply memorise the training rows; consistent models then disagree on every unseen instance. Being consistent with training data is therefore not evidence the model will perform well after deployment — we need a different criterion (Section 7): performance on unseen data.

03From business problem to analytics problem

Before any data is touched, a real-world engineering or business problem must be translated into a precisely defined analytics problem. The lectures structure this as three key questions:

  1. What is the business problem and what are the goals the business wants to achieve?
  2. How does the business currently work? (the existing process or decision that would be supported)
  3. In what ways could an analytical model address the business problem? — what type of model will be created, where and when it will be used, and how it helps.

Answering these questions fixes the five elements every well-defined analytics problem must state:

Definition — the five elements of an analytics problem formulation
  • Decision or process to be supported — e.g. accepting/rejecting customer orders and promising completion dates.
  • Business or engineering objective — e.g. give realistic completion promises without disrupting existing production commitments.
  • Subject of the analysis — the thing each prediction is about, e.g. one customer order (this becomes “one row” in the analytics base table).
  • Required model output — a class label, a probability/score, or a numeric prediction, e.g. predicted working days to completion.
  • How the output will be used — who consumes it and what they do with it, e.g. the production planner sets the promised date and decides whether the order can be accepted.

Illustration (motor-insurance fraud, from the lectures). (1) Problem and goal: despite a fraud team investigating 30% of claims, the insurer still loses money to fraud; investigations cost time and money, and uninvestigated fraud leaks money. (2) Current process: a claim is lodged, validated, and a fraud checklist (risk rating from statement consistency, supporting evidence, previous claim history) decides whether to investigate. (3) Analytics solution: build a model that predicts the likelihood a claim is fraudulent, so the investigation team targets high-risk claims instead of using the checklist.

3.1 Feasibility check

Once the analytic solution is defined, its feasibility must be assessed before proceeding:

  • Are suitable data available? Developing a data-driven model requires historical data — for fraud, a large collection of past claims with labels (fraudulent / non-fraudulent).
  • Will the data be available at prediction time? Every input the model needs must exist at the moment a prediction is required (see feature timing, Section 4.2).
  • Can the organisation act on the insight? A model is only useful if the business can use it — for fraud, the model replaces the checklist and directly drives the investigation decision (capacity to action).
Common mistake

Students often stop at “we have data”. The feasibility check has three legs: historical data to train on, data available when predicting, and an organisation able to act. A question may give you perfect historical data but reveal the process owner will ignore the model — that solution is not feasible.

04Domain concepts and feature design

4.1 Domain concept diagrams

Selecting the features for an analytics base table is based on domain knowledge and on analysis of relationships between features. The recommended starting point is a domain concept diagram — a hierarchy that begins with the analytics solution and branches into high-level abstractions of the prediction subject:

  • Analytics solution (root) → several domain concepts (high-level characteristics of the prediction subject) → domain sub-concepts → concrete features.
  • One branch is special: the target concept → the target feature (what the model must predict).

Reading the diagram gives you the candidate features: each leaf under the descriptive domain concepts is a candidate descriptive feature, and the leaf under the target concept is the target feature.

Example 1 (motor-insurance fraud). Domain concepts include policy details (e.g. age of policy), claim details (incident type, claim amount), claimant history (number of previous claims), claimant links (relationships with other people involved) and claimant demographics (age, gender, occupation); the target concept is the fraud outcome.

Example 2 (study-guide case study: completion time of custom components). The diagram starts at “predict order completion time” and splits into (a) concepts about the submitted design and manufacturing requirements — material, dimensions, tolerances, design complexity, required operations, order quantity — and (b) concepts about the factory state when the order is accepted — machine workloads, queued orders, machine and material availability. The target concept is the actual working days to completion. Each concept is plausible because it can lengthen or shorten production (complex parts need more operations; a loaded factory adds queueing time).

4.2 Raw vs derived features, and feature validity

Raw features are copied directly from the source data (e.g. accident location); derived features are constructed from one or more raw sources (e.g. grouping locations into accident “zones”). When designing features, three data considerations decide whether a feature is usable:

Definition — availability, timing, longevity
  • Availability — data must exist to implement the feature. Example: an “average balance over the past six months” feature is unusable if the company never tracked historical balances.
  • Timing — the data defining a feature must be available before the target is known, i.e. at prediction time. Example: predicting tomorrow’s ice-cream sales cannot use tomorrow’s temperature unless that temperature can itself be predicted accurately.
  • Longevity — data can become stale; the relationship or the source must remain valid over the model’s lifetime. Example: using an applicant’s salary for loan decisions is risky because salaries change over time.

A feature that fails any of these three tests is invalid at deployment, even if it looks brilliant on historical data.

Worked example — screening candidate features (study guide Q4)

Prediction: completion time of a custom-component order, generated when the customer submits the order. Screen each candidate feature on availability, timing and longevity:

  • A — Component material (recorded for all previous orders). Availability: full history ✓. Timing: known at order submission ✓. Longevity: material specifications are stable ✓. Suitable.
  • B — Number of orders waiting for the required machines. Availability: current queue information exists but no historical queue records were retained ✗ — there is nothing to train on. Not suitable (fails availability for model development).
  • C — Design changes requested after production started. Availability: recorded historically ✓. Timing: the value only becomes known after production starts, i.e. after the prediction must already have been made ✗. Not suitable (invalid at deployment — timing).
  • D — Estimated processing time from the current scheduling system. Availability: recorded ✓. Timing: computable at submission ✓. Longevity: the system is being replaced next year and the replacement calculates processing times differently ✗ — the feature’s meaning will change and historical values become inconsistent. Not suitable (longevity).

05The analytics base table

Definition — analytics base table (ABT)

The analytics base table is the flat tabular data structure used to represent a predictive-analytics problem. Each column is a feature (also called attribute, field or variable); the columns divide into descriptive features and a single target feature. Each row is an instance (also called example, record or observation) containing values for both the descriptive features and the target — one subject for which a prediction can be made. This is the “one-row-per-subject” structure.

In the fraud example, each row is one claim (location, time of day, weather, driver licence number, claim amount, … and the target: fraud yes/no). In the completion-time case study, one row is one customer order, the descriptive features describe the component design and factory state, and the target is the actual working days to complete the order. Note that not every analytics solution has a target feature — unsupervised problems (Section 2.1) have only descriptive features.

Organisational data is rarely already in this shape. The ABT is constructed from multiple sources — flat files, operational databases, data warehouses and data marts, external data feeds, and exotic data — by joining sources, filtering rows and fields, deriving new features by combining or transforming existing ones, and aggregating. This construction work happens in the data-preparation phase of CRISP-DM (Section 6).

Common mistake

Getting the row granularity wrong. If the prediction is “how long will this order take?”, one row must be one order. A table with one row per machine, per day, or per operation cannot directly represent that prediction problem, no matter how much data it contains.

06The CRISP-DM process

Definition — CRISP-DM

The CRoss Industry Standard Process for Data Mining (CRISP-DM) is the commonly used approach for solving a data-analytics problem. It defines the six key phases of the data-analytics project lifecycle.

#PhaseWhat happens
1Business understandingThe project starts from a business problem phrased as a question (e.g. “how can revenue be increased?”). Objectives, the current process and how a model would be used are defined (Section 3).
2Data understandingRelevant data is identified and collected; activities are performed to get familiar with it — spotting data issues, discovering first insights (and often generating new questions).
3Data preparationAll relevant data sources are combined into a table-like structure designed for analytics — i.e. the analytics base table is built (joins, filtering, deriving features, aggregation).
4ModellingSeveral models are constructed, from which the best model is selected.
5EvaluationBefore deployment, tests determine whether model performance conforms to quality requirements and business success criteria.
6DeploymentFor a once-off analysis the results are presented; otherwise steps are taken to integrate the model into the organisation’s processes.
The six CRISP-DM phases and their purpose, as presented in the Week 1 lectures.

6.1 Why CRISP-DM projects are iterative

CRISP-DM is explicitly not a strictly sequential waterfall:

  • Even in small projects, moving back and forth between phases is required — e.g. during data understanding, new questions arise that need additional input from the business (back to business understanding).
  • The six phases are typically repeated several times in the same project, each cycle building on the previous one — e.g. evaluation shows the error is too large for the order-acceptance decision, so the team returns to data preparation (new features) or modelling (different algorithms).
Intuition — mapping activities to phases in exams

Ask what the activity produces. Talking to planners about how predictions will be used → business understanding. Hunting missing values and inconsistencies → data understanding. Combining sources into the base table → data preparation. Training models → modelling. Checking errors against the decision’s requirements → evaluation. Feeding predictions into the planners’ system → deployment. (These are exactly the six activities in study-guide Q5.)

07Generalisation, underfitting and overfitting

Definition — generalisation

A model generalises when it performs well not only on the historic instances it was built from but also on unseen instances. Searching for a model is really searching for a model that will generalise — this is the criterion that replaces mere consistency with the training data (Section 2.3), since consistent models can simply memorise and then disagree on unseen data.

The purpose of model evaluation is threefold: (1) to estimate how the model will perform when deployed; (2) to determine which of the developed models is most suited to the task; (3) to convince the business that the model will meet its need. All three require measuring performance on data the model did not train on.

7.1 Underfitting and overfitting

  • Underfitting — the selected model is too simplistic to capture the underlying relationship between the descriptive features and the target feature. It performs poorly on both training and unseen data. Associated with high bias: error from erroneous assumptions in the learning algorithm, which can cause real (possibly complex) relationships to be missed.
  • Overfitting — the selected model is so complex that it fits the data set too closely and becomes sensitive to noise in the data. It performs very well on training data but poorly on unseen data. Associated with high variance: error from sensitivity to small fluctuations in the training set, which causes the algorithm to model the random noise rather than the true relationship.
  • “Just right” — the model strikes a good balance between underfitting and overfitting (low bias, low variance) and will generalise well.

7.2 Hold-out sampling: three data sets, three jobs

Finding the best model requires three data sets, typically split around 70% / 15% / 15% from the available data:

  • Training data (~70%) — model development. Used to fit the model parameters, i.e. to learn the descriptive–target relationship.
  • Validation data (~15%) — model selection. Used to adjust model complexity and compare candidate models, while avoiding multiple-comparison bias: if the test set were used to “find” the best model over possibly hundreds of variations, performance on the test set would be optimistic. The validation set lets you try different models without “peeking” at the final yardstick. Select the model with the smallest validation error.
  • Test data (~15%) — unbiased evaluation. Used once, after model selection, to estimate how the model will perform on unseen data in production. It must not contain any instances from the training or validation sets; otherwise no inference about generalisation is possible.

The validation curve makes the diagnosis concrete: plot training and validation error against model complexity. Underfit models have high training and validation error; as complexity grows both fall; past the sweet spot the model becomes consistent with the training data but fails to generalise — validation error rises while training error keeps falling (validation error >> training error). The best model sits at the minimum of the validation error.

Common mistake — why training performance alone is insufficient

Performance on training data alone never demonstrates that a model will perform well after deployment, because (1) many different models — including pure memorisers — are consistent with any training sample, and they disagree on unseen instances; (2) training error rewards complexity: the more flexible the model, the lower the training error, even when generalisation gets worse. Evidence of future performance requires measurement on data excluded from training (validation/test).

Worked example — diagnosing under/overfitting and selecting a model (study guide Q8)

Three classifiers of increasing complexity for defective/non-defective components:

ModelTraining accuracyValidation accuracyGap (train − val)
A81%79%2 pp
B95%92%3 pp
C100%76%24 pp

1. Diagnosis. Model A: low accuracy on both sets with a small gap — it performs poorly even on data it has seen, so it is too simple to capture the relationship: underfitting (high bias). Model C: perfect training accuracy but a 24-percentage-point collapse on validation data — it has fitted the training set (including its noise) too closely: overfitting (high variance). Model B: high accuracy on both sets with a small gap — the “just right” balance.

2. Selection. Select Model B: model choice is based on validation performance (the estimate of generalisation), and B has the highest validation accuracy (92%).

3. Why not C, which has the highest training accuracy? Training accuracy measures memorisation of the past, not prediction of the future; C’s 76% validation accuracy shows it would perform worst of the three in production. This is exactly why the test/validation data — not the training data — drives selection.

4. Roles of the three sets. Training develops the models; validation compares them and exposes overfitting during selection; the (not yet used) test set will give the final unbiased estimate of the selected model’s deployment performance — used once, after selection.

08Evaluating classification models

8.1 The confusion matrix

A confusion matrix compares predicted values against actual values: instances are grouped by their actual label and their predicted label, which visualises exactly what kinds of errors a model makes. By convention, the outcome that is most important for the business is treated as the positive class (e.g. defective, fraud, churn). For a binary target there are four outcomes:

8.2 Accuracy, precision, recall, F1

\[ \text{Accuracy} = \frac{TP + TN}{TP + FP + FN + TN} \qquad \text{Error rate} = \frac{FP + FN}{TP + FP + FN + TN} \]
TP
True positives: positive instances predicted positive.
TN
True negatives: negative instances predicted negative.
FP
False positives: negative instances predicted positive.
FN
False negatives: positive instances predicted negative.
TP + FP + FN + TN
All instances in the confusion matrix.
Error rate
Fraction misclassified; equal to 1 − accuracy.

Accuracy divides the number of correct predictions (true positives + true negatives) by the total number of predictions.

\[ \text{Precision} = \frac{TP}{TP + FP} \qquad \text{Recall} = \frac{TP}{TP + FN} \]
TP
True positives.
FP
False positives.
FN
False negatives.
TP + FP
Everything the model predicted as positive.
TP + FN
Everything that actually is positive.
  • Precision — “if the model predicts positive, how often is it correct?” It measures how trustworthy positive predictions are (penalised by false positives).
  • Recall — “of all the actual positive cases, how many did we catch?” It measures coverage of the positive class (penalised by false negatives).
\[ F_1 = 2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}} \]
F1
Harmonic mean of precision and recall; high only when both are high.
Precision
Fraction of predicted positives that are correct.
Recall
Fraction of actual positives that were found.

The F1 score is the harmonic mean of precision and recall, ranging from 0 to 1; a classifier with a high F1 must have both good precision and good recall. It is a useful single number when the data set is imbalanced.

Common mistake — accuracy can be misleading

When classes are imbalanced, accuracy rewards ignoring the rare class. Lecture example (churn prediction): a model with a 91% accuracy had predicted churn for only one customer, while a 78%-accuracy model found most churners. Always compare accuracy to the trivial baseline “predict the majority class”, and report precision/recall/F1 alongside it.

Worked example — evaluating a component-inspection model (study guide Q7)

A visual inspection model is evaluated on 200 components not used in training. 20 are actually defective; the model correctly identifies 16 defective components and incorrectly classifies 12 non-defective components as defective. Positive class = defective.

Step 1 — confusion matrix. Actual defective = 20, actual non-defective = 200 − 20 = 180. TP = 16 (defective, flagged); FN = 20 − 16 = 4 (defective, missed); FP = 12 (non-defective, flagged); TN = 180 − 12 = 168.

Predicted defective (+)Predicted non-defective (−)
Actual defective (+)TP = 16FN = 4
Actual non-defective (−)FP = 12TN = 168

Step 2 — metrics.

  • Accuracy = (TP + TN) / 200 = (16 + 168) / 200 = 184 / 200 = 0.920 (92.0%)
  • Precision = TP / (TP + FP) = 16 / 28 = ≈ 0.571 — only ~57% of flagged components are truly defective.
  • Recall = TP / (TP + FN) = 16 / 20 = 0.800 — 80% of actual defects are caught.
  • F1 = 2 × (0.5714 × 0.800) / (0.5714 + 0.800) = 0.9143 / 1.3714 = ≈ 0.667

Step 3 — why accuracy alone is misleading. Only 10% of components are defective. A trivial model that labels every component “non-defective” scores 180/200 = 90% accuracy while catching zero defects. The real model’s 92% is barely above that baseline; the confusion matrix reveals substantial false alarms (12) and missed defects (4) that the single accuracy number hides.

Step 4 — if missing a defect is far costlier than an unnecessary inspection. Focus on recall: it measures the fraction of actual defects caught, and improving it directly reduces false negatives (defects reaching the customer). Some false positives (extra inspections) are the acceptable price.

8.3 Prediction scores and the ROC curve

Most classifiers do not output a class label directly. Instead they produce a prediction score between 0 and 1 (informally, a confidence that the instance is positive), which is only converted into a class label by comparing it to a threshold — conventionally 0.5: at or above the threshold the instance is predicted positive, below it, negative. A well-trained model should push actual negative instances toward scores near 0 and actual positive instances toward scores near 1.

Definition

A confusion matrix (and therefore accuracy, precision, recall, F1) is computed at one fixed threshold. Moving the threshold trades recall against precision: lowering it flags more instances as positive (recall rises, precision typically falls); raising it does the reverse. This threshold-dependence is exactly what the confusion matrix hides.

The receiver operating characteristic (ROC) curve is built by sweeping the threshold from 1 down to 0 and, at each value, plotting the true positive rate (recall, y-axis) against the false positive rate (FP / (FP + TN), x-axis). The resulting curve shows how the model trades recall for false alarms across every possible threshold at once, rather than the single operating point a confusion matrix reveals.

  • Reading the curve: a point on the curve is the (FPR, TPR) pair produced by one specific threshold. As the threshold is lowered, both rates rise (more instances — correctly and incorrectly — are called positive), tracing the curve from the origin (0,0), where nothing is predicted positive, toward (1,1), where everything is.
  • Area under the curve (AUC): summarises the whole curve as a single number between 0 and 1, making it easy to rank or compare models without committing to one threshold. AUC = 0.5 is no better than random guessing; AUC = 1.0 is a perfect ranking of positives above negatives.
  • Why it matters: two models can have identical accuracy at the default 0.5 threshold yet have very different ROC curves — one may be far more useful once the threshold is tuned to the business's actual cost trade-off (Section 8.2's worked example: if missing a defect is costlier than a false alarm, the threshold should be lowered to favour recall, and the ROC curve is what tells you how much precision that costs).

09Evaluating regression models

For regression, the error of each instance is the difference between the target value ti and the model prediction M(di). To get an overall measure, the per-instance errors are aggregated — commonly by summing either absolute or squared errors — and divided by the number of instances so that the measure is comparable across data sets of different sizes.

\[ \text{SSE} = \sum_{i=1}^{n} \big(t_i - M(d_i)\big)^2 \qquad \text{MSE} = \frac{1}{n}\sum_{i=1}^{n} \big(t_i - M(d_i)\big)^2 = \frac{\text{SSE}}{n} \]
ti
Target (true) value of instance i.
di
Descriptive features of instance i.
M(di)
The model's prediction for that instance.
n
Number of instances.
SSE
Sum of squared errors.
MSE
Mean squared error: SSE divided by n.
\[ \text{RMSE} = \sqrt{\text{MSE}} \]
RMSE
Root mean squared error, in the same units as the target.
MSE
Mean squared error.
  • SSE (sum of squared errors) — total squared prediction error; grows with data-set size.
  • MSE (mean squared error) — average squared error; comparable across data sets, but in squared units.
  • RMSE (root mean squared error) — back in the units of the target; interpretable as a typical prediction error. Squaring penalises large errors more than small ones.
\[ R^2 = 1 - \frac{\text{SSE}}{\text{SST}} \qquad \text{where } \text{SST} = \sum_{i=1}^{n} (t_i - \bar{t}\,)^2 \]
R2
Share of the target's variation that the model explains.
SSE
Sum of squared errors of the model.
SST
Total sum of squares: squared deviations of the targets from their mean.
ti
Target value of instance i.
t̄
Mean of the target values.
n
Number of instances.

The R² coefficient is a domain-independent measure: it compares the model against the naive model that always predicts the average target value t. SST is the total sum of squares about the mean — the error the naive model makes. An R² of 0 means the model explains none of the variance (it is no better than predicting the mean); an R² of 1 means it explains all the variability (perfect predictions, SSE = 0).

Common mistake

Sign convention and units: with residual = actual − predicted, a negative residual means the model overestimated. MSE is in squared units and should not be interpreted directly as “days” or “rand” — take the square root (RMSE) first. And R² is computed with SST about the mean of the actual values, not about zero.

Worked example — evaluating completion-time predictions (study guide Q6)

A regression model is evaluated on five completed orders not used in training (residual = actual − predicted):

O102151415 − 14 = +11

1. Residuals and direction. O101 and O103: negative residuals — the model overestimated (by 1 and 2 days). O102 and O104: positive residuals — the model underestimated (by 1 and 2 days). O105: exact.

2. SSE, MSE, RMSE. SSE = 1 + 1 + 4 + 4 + 0 = 10. MSE = 10 / 5 = 2. RMSE = √2 ≈ 1.41 working days.

3. R². Mean actual = (10 + 15 + 20 + 25 + 30) / 5 = 20. SST = (10−20)² + (15−20)² + (20−20)² + (25−20)² + (30−20)² = 100 + 25 + 0 + 25 + 100 = 250. R² = 1 − 10/250 = 1 − 0.04 = 0.96.

4. Interpretation. RMSE ≈ 1.41 days: the model’s typical error is about one and a half working days — small relative to completion times of 10–30 days, so promises based on it are reasonably reliable (bearing in mind the evaluation used only five orders). R² = 0.96: the model explains 96% of the variability in completion times around the mean — its squared error is only 4% of the naive mean-predictor’s, i.e. a very strong fit.
