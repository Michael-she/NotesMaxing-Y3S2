Toolchain, Multi-File Projects & the ARM Stack

CS245 · Lectures 4–6 · Build pipeline, mixing C/assembly, extern, function calls, the stack

01Embedded Toolchain & Compilation Pipeline

  • Cross-compiler (arm-none-eabi-gcc): runs on the host PC (x86_64) but emits machine code targeting the ARMv7-M architecture, with no underlying OS ("bare-metal"). A cross-compiler is, generally, any compiler that creates executable code for a platform other than the one it runs on — typical of embedded development.
  • The compiler, assembler, and linker together are called the toolchain.
  1. Compilation: C source files (.c) → assembly source (.s).
  2. Assembly: assembly files (.s) → relocatable object files (.o).
  3. Linking: the linker uses a linker command script (.ld) to combine .o files and precompiled runtime libraries (.a/.lib) into a single ELF (Executable and Linkable Format, .elf) binary image.
  4. Flashing/debugging: GDB and ST-LINK flash the executable into microcontroller Flash memory, starting at address 0x0800 0000 (aliased to 0x0000 0000).

Build in the IDE is incremental (only changed files recompile); Clean deletes all .o/.elf output so the next Build starts from scratch — useful when you see unexplained behaviour. Debug programs the binary into Flash, starts execution, and lets the IDE pause the processor at breakpoints, single-step, and inspect or modify registers/memory while halted.

02Mixing C and Assembly Code

There are two ways to add ARM assembly to a project:

Method 1 — separate assembly file (.s)

    .global set_leds
    .p2align 2
    .type set_leds, %function
    .syntax unified
set_leds:
    .fnstart
    push {lr}
    lsl  r0, r0, #12        // parameter passed in r0
    ldr  r3, =0x40020C14    // GPIOD_ODR address
    str  r0, [r3]
    pop  {pc}
    .fnend

Method 2 — inline assembly (asm())

Watch outWhitespace or a tab (\t) is required before normal instruction mnemonics (non-labels) inside an inline asm() block.
void set_leds(uint32_t ledstate) {
    asm(
        ".equ led_register, 0x40020C14\n\t"
        "lsl  r0, r0, #12\n\t"
        "ldr  r3, =led_register\n\t"
        "str  r0, [r3]\n\t"
    );
}

03Multi-File Projects: extern & Header Files

Often a global variable or function defined in one .c file needs to be used from another. Simply referencing it from a second file fails to compile — the compiler has no idea it exists ("count undeclared").

Solution: declare it extern in the file that uses it (or, better, in a shared header), and define it exactly once in its own .c file.

Rules
  • Never #include a .c file — only .h files.
  • Always use extern for variables declared in a header — the implication is that a variable is never defined in the header, only made visible (exported) from it.
  • Declare function prototypes and extern variables in .h files; define the actual variables/functions once, in the matching .c file.

04Global vs. Local Variables & Style

DeclaredVisible fromLives in
Global variableOutside any functionAny functionDATA (if initialised) or BSS (if not) segment
Local variableInside a functionOnly that functionThe STACK — created when the function starts, and freed (reused) when it returns

See the Theory notes for this week for where DATA/BSS/STACK physically sit in the memory map.

Practical tips

  • Always initialise variables before use — an uninitialised local variable holds whatever garbage was last in that stack slot (the compiler will typically warn, e.g. 'maxVal' is used uninitialized in this function).
  • Declare all local variables near the top of a function, and all global variables near the top of the source file — this keeps their scope easy to see at a glance.
  • Avoid giving a local variable the same name as a global one, even though C allows it (the local one silently "shadows" the global inside that function).
  • Use descriptive names, and camelCase for variables and functions, e.g. newString, getNewString().
  • Keep global variables to a minimum — passing state through function arguments instead of shared globals keeps functions reusable with different inputs and easier to reason about (better modularity).

Dynamic memory allocation

Use malloc() and free() (from <stdlib.h>) to allocate and release memory from the HEAP at run time.

05Linker Script Mechanics

The linker script tells the linker exactly where each section of the program should be placed in the address space. A simplified example (sizes here are illustrative — see the datasheet's memory map for the exact Flash/SRAM sizes on this board):

MEMORY
{
    FLASH (RX)  : ORIGIN = 0x08000000, LENGTH = 1024K
    RAM   (RWX) : ORIGIN = 0x20000000, LENGTH = 192K
}

SECTIONS
{
    /* Startup / vector table goes first, into FLASH */
    .isr_vector : { ... } >FLASH

    /* Program code goes into FLASH */
    .text : { ... } >FLASH

    /* Constant data (read-only) goes into FLASH */
    .rodata : { ... } >FLASH

    _sidata = LOADADDR(.data);

    /* Initialised data: lives in RAM at runtime, but its
       initial values are loaded from a copy kept in FLASH  */
    .data : { ... } >RAM AT> FLASH

    /* Uninitialised data: zero-filled by startup code */
    . = ALIGN(4);
    .bss : { ... } >RAM
}

The key idea: .data is mapped to run in RAM (>RAM) but its initial values are stored (loaded) from Flash (AT> FLASH) — startup code copies that image from Flash into RAM before main() runs. .bss holds no data in the binary at all; startup code simply zeroes that RAM range.

06Function Calls & Branching

MnemonicNameMeaning
B <label>BranchSimple branch to an address, optionally conditional (e.g. BGT).
BX <reg>Branch and ExchangeBranch to an address held in a register — commonly BX LR to return from a function.
BL <label>Branch with LinkStores the address of the next instruction into LR, then branches — this is how a C function call is implemented.
BLX <reg>Branch with Link and ExchangeSame as BL, but the target address is held in a register.
CBZ / CBNZCompare and branch if (non-)zeroCombines a compare-with-zero and a conditional branch in one instruction.
IT blocksIf-ThenExecutes up to 4 conditional instructions without the pipeline cost of branching.

For ordinary (non-branching) instructions, the Program Counter simply increments by 4 after every instruction (ARM instructions are 4 bytes, and the architecture is byte-addressed) — execution is sequential. A branch instruction changes the PC directly, and each branch flushes the pipeline (a refill penalty of 1–3 cycles), since the CPU cannot know in advance whether a conditional branch will be taken.

Worked example — function call and return

int main() {
    int y;
    y = diffofsums(5, 4, 3, 2);
    ...
}
diffofsums(int f, int g, int h, int i) {
    int result;
    result = (f + g) - (h + i);
    return result;
}
MAIN:
    mov R0, #5        // argument 0 = 5
    mov R1, #4        // argument 1 = 4
    mov R2, #3        // argument 2 = 3
    mov R3, #2        // argument 3 = 2
    bl  DIFFOFSUMS    // call function (LR = return address)
    mov R4, R0        // y = returned value
    b   DONE
DIFFOFSUMS:
    add R0, R0, R1    // R0 = f + g
    add R2, R2, R3    // R2 = h + i
    sub R0, R0, R2    // result = (f + g) - (h + i)
    mov PC, LR        // return to caller  (equivalently: BX LR)
DONE:

BL and MOV PC, LR (or the equivalent BX LR) are the two essential instructions for a call and return: BL stores the return address in LR and branches; the callee returns by copying LR back into PC.

Nested calls need the stack

If func1 calls func2 using BL, the second BL overwrites LR (and probably R0–R3) — func1 now has nowhere to return to. The LR value must therefore be saved somewhere before making a nested call. That "somewhere" is the stack.

07AAPCS: The ARM Calling Convention

The ARM Architecture Procedure Call Standard (AAPCS) is the contract between a calling function and a called function, so that hand-written assembly interoperates correctly with C.

  • Parameter passing: the first four 32-bit arguments go in R0–R3, left to right. A double-word argument (e.g. a 64-bit value) is passed in a consecutive pair of registers (R0:R1 or R2:R3). Additional arguments beyond the first four are passed on the stack.
  • Return value: R0 (or R0:R1 for a 64-bit / double-word result).
  • Corruptible / scratch registers: R0, R1, R2, R3, R12 — the caller must save these first if it needs their values to survive the call.
  • Callee-saved / preserved registers: R4–R8, R10, R11, and SP (R13) — a function using these as scratch space must save and restore their original contents before returning.

08The Stack Pointer & Push/Pop Mechanics

  • SP (R13) is an ordinary register that, by convention, holds the address of the top of the stack. It starts at a high address and decrements as the stack grows.
  • ARM does not have dedicated push/pop hardware — it uses ordinary load/store instructions, with the compiler (or the assembly programmer) applying an auto increment/decrement to SP.
PUSH (Full Descending): POP (Full Descending): 1. SP = SP − 4 1. data = *SP 2. *SP = data 2. SP = SP + 4
SP
Stack pointer: the address of the top of the stack.
*SP
The memory word at the address held in SP.
data
The 32-bit value being pushed or popped.
4
Bytes in one 32-bit word.
Full Descending
SP points at the last item stored, and the stack grows towards lower addresses.

Worked example: stack base 0x0008 0000, SP currently 0x0007 FFDC (9 elements on the stack).

  • Push 0x8359 6900: SP decrements first to 0x0007 FFD8, then the value is stored there — stack now has 10 elements.
  • Pop: the word at the current SP (0x0007 FFDC) is read first (e.g. 0x1100 49FF), then SP increments to 0x0007 FFE0 — stack now has 8 elements.
  • The empty-stack value of SP here is 0x0008 0000 — the base address.

09Saving Registers & Multiple Load/Store

A function should compute its return value and otherwise have no side effects on registers it does not own. The naive version of diffofsums below violates this — it clobbers R4, R8, and R9:

DIFFOFSUMS:
    add R8, R0, R1    // R8 = f + g
    add R9, R2, R3    // R9 = h + i
    sub R4, R8, R9    // result = (f + g) - (h + i)
    mov R0, R4        // put return value in R0
    mov PC, LR         // return to caller

Fix: save the registers being used on the stack before modifying them, and restore them before returning:

DIFFOFSUMS:
    sub SP, SP, #12    // make space on the stack for 3 registers
    str R9, [SP, #8]   // save R9
    str R8, [SP, #4]   // save R8
    str R4, [SP]       // save R4
    add R8, R0, R1     // R8 = f + g
    add R9, R2, R3     // R9 = h + i
    sub R4, R8, R9     // result = (f + g) - (h + i)
    mov R0, R4         // put return value in R0
    ldr R4, [SP]       // restore R4
    ldr R8, [SP, #4]   // restore R8
    ldr R9, [SP, #8]   // restore R9
    add SP, SP, #12    // deallocate stack space
    mov PC, LR          // return to caller

LDM / STM — load/store multiple

Loading or storing one 32-bit word at a time with LDR/STR is tedious for several registers at once. LDM/STM transfer several registers to/from consecutive memory addresses in one instruction:

LDM r10, {r0, r2, r5-r7}   ; load 5 consecutive words starting at [r10]
                            ; into r0, r2, r5, r6, r7

; Equivalent to:
LDR r0, [r10]
LDR r2, [r10, #4]
LDR r5, [r10, #8]
LDR r6, [r10, #12]
LDR r7, [r10, #16]

The suffix indicates direction: -IA (increment after) or -DB (decrement before). Combined with the stack conventions, ARMv7-M supports both Full Descending (-FD) and Empty Ascending (-EA) stacks:

Stack typeStoreLoad
Full descendingSTMFD (= STMDB, decrement before)LDMFD (= LDM/LDMIA, increment after)
Empty ascendingSTMEA (= STM/STMIA, increment after)LDMEA (= LDMDB, decrement before)

PUSH/POP are not separate real instructions — they are simply assembler aliases for STMDB/LDMIA against SP:

PUSH {r0, r2}   ≡  STMDB sp!, {r0, r2}
POP  {r0, r2}   ≡  LDMIA sp!, {r0, r2}

PUSH {r4, lr}   ≡  STMDB sp!, {r4, lr}
POP  {r4, pc}   ≡  LDMIA sp!, {r4, pc}   // pops straight into PC = return!
